\section{Eclipse Leda Overview}
\label{sec:leda-overview}

Eclipse Leda \cite{EclipseLeda2023} is an SDV distribution built on the
Yocto Project. It packages a curated set of Eclipse SDV middleware
components --- Mosquitto MQTT broker, Kuksa databroker, Kanto container
manager, and OpenTelemetry collector --- into a bootable image that runs
on QEMU (x86-64) or on supported ARM hardware such as the Raspberry Pi~4.
Its primary purpose is to serve as a reference platform for developing
and validating SDV software stacks before deploying to a real vehicle
ECU.

SHILATE targets the QEMU image
(\texttt{sdv-image-all-qemux86-64.wic.qcow2}) included in the
repository. The \texttt{leda/run-leda.sh} script launches the image with
a bridged network interface so that the host machine and the QEMU guest
share a Mosquitto broker at \texttt{127.0.0.1:1883}.

\section{MQTT-to-Kuksa Bridge}
\label{sec:feeder}

The \texttt{mqtt-kuksa-feeder} container subscribes to the
\texttt{vehicle/\#} wildcard on the Mosquitto broker and forwards each
received message to the Kuksa databroker \cite{EclipseKuksa2024} as a
VSS path write via gRPC. The topic-to-VSS mapping is shown in
\cref{table:vss-map}.

\begin{table}[H]
\caption{MQTT topic to VSS path mapping.}
\label{table:vss-map}
\begin{tabular}{|p{5cm}|p{7cm}|}
  \hline
  \textbf{MQTT topic} & \textbf{VSS path} \\
  \hline
  \texttt{vehicle/speed}    & \texttt{Vehicle.Speed} \\
  \hline
  \texttt{vehicle/rpm}      & \texttt{Vehicle.Powertrain.CombustionEngine.Speed} \\
  \hline
  \texttt{vehicle/steering} & \texttt{Vehicle.Chassis.SteeringWheel.Angle} \\
  \hline
  \texttt{vehicle/brake}    & \texttt{Vehicle.Chassis.Brake.PedalPosition} \\
  \hline
  \texttt{vehicle/throttle} & \texttt{Vehicle.OBD.ThrottlePosition} \\
  \hline
\end{tabular}
\end{table}

After the feeder writes a signal, any subscriber --- including the
Velocitas vehicle application --- is notified with the new value within
the same event loop tick.

\section{Velocitas Vehicle Application}
\label{sec:velocitas}

The Velocitas vehicle application \cite{EclipseVelocitas2024}
implements the operational safety monitor for the RL agent. It subscribes
to five VSS signals via the Kuksa databroker, logs a telemetry summary
every 5 seconds, and enforces two hard limits:
\begin{itemize}[topsep=1.15pt,itemsep=1.15pt]
  \item \textbf{Overspeed}: if \texttt{Vehicle.Speed} exceeds 120~km/h,
    an alert is published to \texttt{leda/command/alert} with payload
    \texttt{\{"type":"overspeed","value":<speed>\}}.
  \item \textbf{RPM redline}: if engine RPM exceeds 6500, an analogous
    alert is published.
\end{itemize}
Alerts are currently informational; the architecture is designed so that
the safety monitor can be upgraded to a command-injection path without
modifying any other component.

\section{Container Deployment}
\label{sec:containers}

All three service containers (\texttt{leda-controller},
\texttt{mqtt-kuksa-feeder}, \texttt{velocitas-app}) ship with Dockerfiles
producing minimal Python~3.11 slim images. Each is described by a Kanto
container manifest (\texttt{kanto-manifest.json}) specifying the OCI
image reference, environment variables
(\texttt{MQTT\_HOST}, \texttt{MQTT\_PORT}, \texttt{MODE},
\texttt{MODEL\_PATH}), and restart policy. Provisioning is automated by
\texttt{leda/provision-device.sh}, which uses SSH to copy manifests to
the Leda device and invoke the Kanto CLI to pull and start the
containers.

\section{Leda Telemetry Broker}
\label{sec:telemetry-broker}

In addition to MQTT, the Leda image runs a lightweight telemetry broker
implemented in Rust. The broker listens on TCP port~7878 and acts as a
multiplexing relay: any client that connects and sends telemetry data has
that data forwarded to all other connected clients. This enables tools
such as \texttt{netcat} or custom dashboards to observe the live
telemetry stream without subscribing to individual MQTT topics.

\section{Raspberry Pi Deployment}
\label{sec:pi-deploy}

In addition to the QEMU-based Eclipse Leda workflow, SHILATE supports
deploying the full inference stack directly onto a \textbf{Raspberry
Pi~4} running standard Raspberry Pi OS (Debian Bookworm). This path
eliminates QEMU virtualisation overhead and produces a portable hardware
inference node that the Unity Editor on a developer workstation connects
to over a LAN. The Pi runs all five SHILATE services as Docker containers
and listens on the standard MQTT port~1883, reachable from Windows Unity.

\subsection{Container Stack}
\label{sec:pi-stack}

The Pi deployment is defined in \texttt{leda/docker-compose.pi.yml}. All
services use \texttt{network\_mode: host} so they share the Pi's network
namespace without any port-mapping configuration, and intra-stack
communication uses \texttt{localhost}. The five containers are described
in \cref{table:pi-services}.

\begin{table}[H]
\caption{Docker services in the Raspberry Pi deployment stack.}
\label{table:pi-services}
\begin{tabular}{|p{5.2cm}|p{6.3cm}|}
  \hline
  \textbf{Container} & \textbf{Role} \\
  \hline
  \texttt{shilate-mosquitto} &
    Eclipse Mosquitto~2 MQTT broker. The volume-mounted
    \texttt{mosquitto.conf} configures a single listener on port~1883
    bound to all interfaces (\texttt{listener 1883}), with anonymous
    access permitted (\texttt{allow\_anonymous true}). \\
  \hline
  \texttt{shilate-kuksa-databroker} &
    Eclipse Kuksa.VAL databroker. Exposes a gRPC endpoint on
    port~30555 with \texttt{--insecure} for development use.
    Stores the current value of each VSS signal path. \\
  \hline
  \texttt{shilate-mqtt-kuksa-feeder} &
    Bridges the \texttt{vehicle/\#} MQTT wildcard to VSS writes in
    the Kuksa databroker via gRPC, enabling the Velocitas application
    to observe simulation telemetry. \\
  \hline
  \texttt{shilate-velocitas-app} &
    Velocitas safety application. Monitors \texttt{Vehicle.Speed}
    (limit: 120~km/h) and engine RPM (limit: 6500) via the Kuksa
    databroker and publishes alerts to \texttt{leda/command/alert}. \\
  \hline
  \texttt{shilate-leda-controller} &
    The RL inference controller (\texttt{MODE=inference}).
    Loads the checkpoint volume-mounted at \texttt{/model/best\_model.zip},
    connects to Mosquitto at \texttt{MQTT\_HOST=127.0.0.1},
    and drives the Unity simulation over MQTT.
    \texttt{RAY\_COUNT=21} matches the simulation's sensor
    configuration. \\
  \hline
\end{tabular}
\end{table}

\subsection{Build and Deployment Automation}
\label{sec:pi-build}

The \texttt{leda/deploy-pi.sh} script automates the entire
build-and-deploy cycle from the developer's workstation. It proceeds
through the following stages:

\begin{enumerate}[leftmargin=2cm,topsep=1.15pt,itemsep=1.15pt,partopsep=1.15pt,parsep=1.15pt]
  \item \textbf{Preflight checks.} SSH connectivity to the Pi user
    \texttt{tetrix@10.122.6.115} is tested. The script verifies that
    Docker and a compatible \texttt{docker compose} version are available
    on the Pi, and installs them via \texttt{apt-get} if not.
    On the build host, ARM64 emulation support is verified via
    \texttt{docker buildx}; if absent, the QEMU binfmt handler is
    installed automatically with
    \texttt{docker run --privileged tonistiigi/binfmt --install arm64}.
  \item \textbf{ARM64 image builds.} Each service that ships a custom
    Dockerfile (\texttt{leda-controller}, \texttt{mqtt-kuksa-feeder},
    \texttt{velocitas-app}) is built for the \texttt{linux/arm64}
    platform using \texttt{docker buildx build --platform linux/arm64
    --load}. The resulting images are saved as \texttt{.tar} archives
    in \texttt{/tmp/}.
  \item \textbf{Asset transfer.} All image archives, the compose file,
    and the \texttt{mosquitto.conf} configuration are copied to
    \texttt{\textasciitilde/shilate/} on the Pi via \texttt{scp}.
  \item \textbf{Load and start.} Each image archive is loaded into
    the Pi's Docker daemon with \texttt{docker load}. Finally,
    \texttt{docker compose -f docker-compose.pi.yml up -d} starts
    all five containers with the \texttt{unless-stopped} restart
    policy.
\end{enumerate}

Partial deployment is supported: invoking the script with the argument
\texttt{feeder}, \texttt{app}, \texttt{controller}, or \texttt{all}
rebuilds and redeploys only the specified component, reducing iteration
time when a single service is updated.

\subsection{Unity-to-Pi Connection Workflow}
\label{sec:unity-pi}

Once the Pi stack is running, the Unity Editor connects to it over the
LAN. The MQTT host in \texttt{TrainingSettings} must be set to the
Pi's IP address and port (\texttt{10.122.6.115:1883}). The
\textit{Remote} mode of the Training Controller
(see \cref{sec:editor-window}) automates the full connection sequence:

\begin{enumerate}[leftmargin=2cm,topsep=1.15pt,itemsep=1.15pt,partopsep=1.15pt,parsep=1.15pt]
  \item The user presses \textit{Run Model} in the Training Controller
    and dismisses the file picker without selecting a local checkpoint.
  \item The window terminates any locally running \texttt{mosquitto.exe}
    and Python processes to free port~1883 on the host.
  \item Unity enters Play mode. \texttt{ConfigureSceneAndLaunch()} runs
    and calls \texttt{LedaBroker.Configure("10.122.6.115", 1883, "env0")},
    overriding the inspector default of \texttt{localhost}.
  \item \texttt{LedaBroker} connects to the Pi's Mosquitto broker.
    The Pi's \texttt{leda-controller} container, which is already
    subscribed to \texttt{env0/vehicle/training/obs}, begins receiving
    observations from Unity and publishing control commands in response.
  \item The Training Controller toolbar displays \textbf{[REMOTE]} in
    amber. Episode-end events and heartbeats are received by the Editor's
    MQTT listener and displayed in the snapshot row and issue log.
  \item When the session ends (Stop button or Play mode exit), the
    Editor fires a background task to restart the local Windows Mosquitto
    service, restoring the host to its original state.
\end{enumerate}
